# SlowPost — описание текущего состояния

## 1. Общая архитектура

SlowPost — файловый транспортный подуровень, работающий поверх Puheg (медленной ад хок сети, инфраструктуру которой создают ноды). Этот слой управляет движением пакетов по сети и их маршрутизацией, что для пользователя может выглядеть как работа с обыкновенным сетевым интерфейсом в обыкновенной локальной сети. Для работы SlowPost так же нужен драйвер (pclient), который связывает меж собой TCP/IP стек ОС и МАС-уровень Puheg, интерпретируя MAC-адреса в IP и оборачивая данные в "сообщения пухег верхнего уровня" - это примерно то же самое, что АТ-команды, только в виде JSON. Слоупост общается с Пиклиентом посредством EventBus - шины сообщений на 127.0.0.1:<9400 по дефолту>. В эту шину подписчикам транслируются разные сообщения, с которыми те работают.

Так как этот сетевой транспорт родился из утилиты, аналогичной Scp (копирование файлов между компьютерами) и с маслями об UUCP, то и выглядит в настоящее время все как копирование файлов между компьютерами. В целом процесс описан в п.4.1

## 2. Структура каталогов

Вся работа Слоупоста строится вокруг файловой системы — это намеренное решение, унаследованное от прародителя-утилиты копирования. Вместо абстрактных очередей и потоков — обычные каталоги, в которые можно заглянуть, переместить файлы руками, или даже отредактировать их содержимое. Пользователь взаимодействует с системой ровно так же, как с электронной почтой: кладёт файл в папку отправителя, и через какое-то время тот появляется в папке получателя.

```
<workDir>/<myIp>/
├── outbox/                          ← исходящее
│   ├── <peerIp>/                    ← каталог конкретного получателя
│   │   ├── report.pdf               ← сюда кладёт пользователь
│   │   ├── work/                    ← то, что сейчас нарезается/отправляется
│   │   └── sent/                    ← успешно доставленное
│   │
│   └── spool/                       ← "почтовая сумка" с чанками
│       ├── <peerIp>/<uuid>/         ← одна конкретная передача
│       │   ├── *.pdf                ← чанки, ещё не упакованные в пакеты
│       │   ├── waiting/             ← чанки, отправленные и ждущие подтверждения
│       │   └── approved/            ← чанки, подтверждённые получателем
│       └── *.pwp                    ← готовые пакеты в корне спула
│
└── inbox/                           ← входящее
    └── <peerIp>/                    ← каталог конкретного отправителя
        ├── report.pdf               ← собранный финальный файл
        └── <uuid>/                  ← чанки передачи в процессе сборки
            ├── *.pdf                ← чанки, уже подтверждённые пруфом
            └── waiting/             ← чанки, ждущие отправки пруфа
```

Имена чанков следуют одному шаблону: `<часть>-<всего>-<ретраи>-<имя_файла>`. Например, `2-5-0-report.pdf` — это третий чанк из пяти для файла `report.pdf`, ещё ни разу не переотправлявшийся. Счётчик ретраев наращивается, если отправка не прошла.

## 3. Формат пакетов

В основе протокола лежит пакетный формат, названный по имени сети — **Puheg Words**. Это набор двоичных кадров, которые передаются поверх сообщений Пиклиента.

### 3.1. Общий вид

Каждый пакет начинается с трёхбайтового магика `PW\x01`, по которому приёмная сторона понимает, что это именно пакет Слова. Сразу за магиком идёт тип кадра, определяющий его содержимое:

```
'P' | 'W' | 0x01 | type | тело
```

Типы кадров:
- `'F'` — файловый кадр, несёт чанк или пруф
- `'0'` — пруф в чистом виде (зарезервирован, сейчас не используется)
- `'C'` — командный кадр (зарезервирован)

### 3.2. Кадр 'F' — файловый

Это основной кадр протокола. Им передаются и сами чанки файла, и пруфы — пруф это просто чанк специального файла с именем `PF`.

```
Смещ.  Размер  Поле
─────  ──────  ────
0      1       'F' — тип кадра
1      2       finalDest — MAC непосредственного получателя
3      2       origin — MAC изначального отправителя (пригодится при маршрутизации)
5      1       размер имени файла
6      N       имя файла
6+N    4       uuid передачи (32 бита)
10+N   1       totalParts — сколько всего чанков в передаче
11+N   1       part — номер этого чанка
12+N   ...     содержимое чанка
```

Все многобайтовые поля передаются в сетевом порядке (старший байт первым).

### 3.3. Пруф — особый файловый кадр

Пруф это обычный файловый кадр с именем `PF`. Его содержимое — массив байтов, каждый из которых есть номер подтверждённого чанка. Например, содержимое `[0, 2, 3]` говорит о том, что получатель подтверждает чанки 0, 2 и 3.

Такой подход позволяет не вводить отдельный тип кадра для подтверждения и использовать для пруфов всю ту же инфраструктуру отправки: спул, упаковку, ретраи.

## 4. Протокол передачи

### 4.1. Отправка файла — путь чанка от каталога до эфира

Когда пользователь кладёт файл в `outbox/<peerIp>/`, начинается следующий процесс:

1. **Сканирование.** Слоупост периодически смотрит в каталоги `outbox/`, находит там новые файлы.

2. **Нарезка.** Найденный файл нарезается на чанки (по умолчанию 2000 байт). Каждый чанк сохраняется в `spool/<peerIp>/<uuid>/` под именем с номером части. Исходный файл перемещается в `outbox/<peerIp>/work/`, где находится до окончания передачи.

3. **Упаковка.** Из каждой передачи берётся самый старый чанк, заворачивается в кадровое представление и сохраняется как `.pwp` в корне спула. Сам чанк при этом перемещается в подкаталог `waiting/` той же передачи — это резервная копия на случай ретрая.

4. **Отправка.** Из очереди `.pwp` выбирается пакет, готовый к отправке (с учётом задержек между отправками и ретраями), и передаётся в шину сообщений. Пиклиент доставляет его до адресата.

5. **Подтверждение.** Если Пиклиент ответил, что передача прошла успешно, Слоупост ждёт пруфа от получателя. Когда пруф приходит (см. 4.3), чанк перемещается из `waiting/` в `approved/`. Если пруф не приходит, через время чанк будет переотправлен.

6. **Завершение.** Когда все чанки передачи оказываются в `approved/`, исходный файл перемещается из `work/` в `sent/`, а каталог передачи в спуле удаляется.

### 4.2. Приём файла — от эфира до готового файла

Когда на станцию приходит кадровый пакет, приёмная сторона:

1. **Сохраняет чанк** во временный каталог `inbox/<peerIp>/<uuid>/waiting/`.

2. **Первый чанк** (когда в `waiting/` один файл и больше ничего нет) сразу подтверждается **одиночным пруфом** — получателю отправляется пруф с единственным номером. Сам чанк при этом перемещается из `waiting/` в корень каталога передачи, помечаясь как подтверждённый.

3. **Последующие чанки** копятся в `waiting/`, пока не соберутся все или не истечёт таймаут.

4. **Когда все чанки на месте**, отправляется **общий пруф** со всеми номерами, чанки перемещаются в корень каталога, склеиваются в итоговый файл в `inbox/<peerIp>/`, а каталог передачи удаляется.

5. **Таймаут.** Если в `waiting/` остались чанки и с момента прихода последнего прошло более 5 минут, общий пруф отправляется повторно. Время последнего чанка при этом обновляется, чтобы не слать пруфы слишком часто.

### 4.3. Обработка пруфов — как отправитель узнаёт о доставке

Когда отправитель получает кадровый пакет с именем `PF`, он:

1. Находит в спуле передачу с указанным `uuid`.
2. Для каждого номера из содержимого пруфа перемещает соответствующий чанк из `waiting/` в `approved/`.
3. Если все чанки передачи подтверждены — завершает передачу (см. 4.1, шаг 6).

Для файлов пруфов действует упрощённая логика: как только Пиклиент подтвердил успешную отправку пруфа, он сразу считается доставленным, и чанк перемещается в `approved/` без ожидания ответного пруфа. Это избавляет систему от бесконечного ожидания подтверждения на подтверждение.

## 5. Жизненный цикл файла

Полный путь файла при отправке:

```
Пользователь кладёт файл
        ↓
  outbox/<ip>/report.pdf
        ↓ scanOutboxAll + spoolFile
  spool/<ip>/<uuid>/0-N-0-report.pdf ... (N-1)-N-0-report.pdf
  outbox/<ip>/work/report.pdf
        ↓ prepareWaitingPackets
  spool/<ip>/<uuid>/waiting/0-N-0-report.pdf
  spool/0-N-0-<ip>-<uuid>.pwp
        ↓ отправка через шину
        ↓ получили пруф
  spool/<ip>/<uuid>/approved/0-N-0-report.pdf
        ↓ все чанки в approved
  outbox/<ip>/sent/report.pdf
  spool/<ip>/<uuid>/ удалён
```

Полный путь файла при приёме:

```
Пришёл кадровый пакет
        ↓
  inbox/<ip>/<uuid>/waiting/0-N-report.pdf
        ↓ первый чанк → отправлен одиночный пруф
  inbox/<ip>/<uuid>/0-N-report.pdf
        ↓ все чанки → отправлен общий пруф, склейка
  inbox/<ip>/report.pdf
  inbox/<ip>/<uuid>/ удалён
```

## 6. Основные компоненты

**`File`** — сердце системы. Управляет спулом: сканирует исходящее, нарезает файлы, упаковывает чанки в пакеты, принимает входящие чанки, собирает из них файлы.

**`Proof`** — логика подтверждений. Создаёт файлы пруфов для отправки и обрабатывает входящие, перенося чанки по каталогам.

**`Words`** — кодирование и декодирование кадров. Здесь всё знание о бинарном формате протокола.

**`EBParser`** — разбор сообщений из шины. Понимает, что пришло из Пиклиента, и передаёт это в нужные обработчики.

**`Transport`** — общение с шиной сообщений. Знает, как подписаться, как отправлять, как слушать.

**`main`** — главный цикл. Раз в секунду опрашивает события, запускает сканирование, отправку, обработку подтверждений.

## 7. Настройки

Основные параметры, которыми можно управлять:

| Параметр | Что делает | По умолчанию |
|----------|-----------|--------------|
| `chunkSize` | размер чанка в байтах | 2000 |
| `maxTransfers` | сколько передач может идти одновременно | 4 |
| `maxProcessRetries` | сколько раз можно переотправить один чанк | 3 |
| `sendTXDelay` | пауза между отправками, мс | 1000 |
| `sendRetryDelay` | пауза перед повторной отправкой, с | 60 |
| `proofTimeout` | таймаут ожидания пруфа, с | 300 |

## 8. Что работает и что впереди

**Работает сейчас:**
- отправка и приём файлов по одному чанку
- одиночные и общие пруфы
- ретраи при неудачных отправках
- таймауты и повторные подтверждения
- уборка завершённых передач

**Ждёт своего часа:**
- маршрутизация пакетов через промежуточные ноды
- криптография (аутентификация и шифрование)
- статистика передачи
- приоритеты передач
