# SlowPost — описание текущего состояния

## 1. Общая архитектура

SlowPost — файловый транспортный подуровень, работающий поверх Puheg (медленной ад хок сети, инфраструктуру которой создают ноды). Этот слой управляет движением пакетов по сети и их маршрутизацией, что для пользователя может выглядеть как работа с обыкновенным сетевым интерфейсом в обыкновенной локальной сети. Для работы SlowPost так же нужен драйвер (pclient), который связывает меж собой TCP/IP стек ОС и МАС-уровень Puheg, интерпретируя MAC-адреса в IP и оборачивая данные в "сообщения пухег верхнего уровня" - это примерно то же самое, что АТ-команды, только в виде JSON. Слоупост общается с Пиклиентом посредством EventBus - шины сообщений на 127.0.0.1:<9400 по дефолту>. В эту шину подписчикам транслируются разные сообщения, с которыми те работают.

Так как этот сетевой транспорт родился из утилиты, аналогичной Scp (копирование файлов между компьютерами) и с маслями об UUCP, то и выглядит в настоящее время все как копирование файлов между компьютерами. В целом процесс описан в п.4.1

## 2. Структура каталогов

```
<workDir>/<myIp>/
├── outbox/
│   ├── <peerIp>/                     ← файлы от пользователя
│   │   ├── report.pdf                ← положить сюда для отправки
│   │   ├── work/                     ← в процессе обработки
│   │   │   └── report.pdf
│   │   └── sent/                     ← успешно отправленные
│   │       └── report.pdf
│   │
│   └── spool/
│       ├── <peerIp>/
│       │   └── <uuid>/               ← передача
│       │       ├── 0-5-0-report.pdf  ← чанки (не отправлены)
│       │       ├── 1-5-0-report.pdf
│       │       ├── waiting/          ← отправлены, ждём пруф
│       │       │   └── 2-5-0-report.pdf
│       │       └── approved/         ← пруф получен
│       │           └── 0-5-0-report.pdf
│       │
│       └── *.pwp                     ← готовые к отправке пакеты
│
└── inbox/
    └── <peerIp>/
        ├── final-file.pdf            ← собранный финальный файл
        └── <uuid>/                   ← приём передачи
            ├── 0-5-report.pdf        ← подтверждённые чанки
            └── waiting/              ← ждём отправки пруфа
                └── 1-5-report.pdf
```

**Имена файлов чанков**: `<part>-<total>-<retries>-<filename>`
- `part` — номер части (0..total-1)
- `total` — общее количество частей
- `retries` — счётчик ретраев
- `filename` — оригинальное имя файла

## 3. Формат пакетов Puheg Words (PW)

### 3.1. Магик и конверт

Все пакеты начинаются с магика `PW\x01` (3 байта).

```
Offset  Size  Field
──────  ────  ─────
0       1     'P'
1       1     'W'
2       1     0x01
3       1     type: 'F' file | '0' proof | 'C' command
4       ...   тело пакета
```

### 3.2. Кадр 'F' — чанк файла

```
Offset  Size  Field
──────  ────  ─────
0       1     type = 'F'
1       2     finalDest (MAC получателя, big-endian)
3       2     origin (MAC изначального отправителя)
5       1     nameSize
6       N     name (чистое имя файла, без служебных пометок)
6+N     4     uuid (32 бита, big-endian)
10+N    1     totalParts
11+N    1     part
12+N    ...   content (содержимое чанка)
```

**Пример**: файл `report.pdf`, чанк 2 из 5:
```
'F' | 0x06 0x54 | 0x06 0x55 | 10 | "report.pdf" | uuid | 5 | 2 | <данные>
```

### 3.3. Кадр '0' — пруф

Пруф отправляется как обычный файл с именем `PF` и расширением `.pwproof`:

```
Offset  Size  Field
──────  ────  ─────
0       1     type = 'F'  (пруф — это тоже F-кадр)
1       2     finalDest
3       2     origin
5       1     nameSize = 2
6       2     "PF"
8       4     uuid передачи
12      1     totalParts = 1
13      1     part = 0
14      ...   content: [0x00, 0x01, 0x02, ...] — номера подтверждённых частей
```

### 3.4. Имя файла пруфа

Файл пруфа на диске: `<uuid>.pwproof` в `outbox/<peerIp>/`

Содержимое — байты номеров подтверждённых частей:
- `0x00` — подтверждён чанк 0
- `0x00 0x01 0x02` — подтверждены чанки 0, 1, 2

## 4. Протокол передачи файлов

### 4.1. Отправка

```
1. Пользователь кладёт файл в outbox/<peerIp>/
2. scanOutboxAll() находит файл
3. spoolFile() нарезает на чанки в spool/<peerIp>/<uuid>/
4. Файл перемещается в outbox/<peerIp>/work/
5. prepareWaitingPackets() берёт самый старый чанк:
   - Оборачивает в PW-кадр
   - Переносит чанк в waiting/
   - Сохраняет .pwp в корне spool/
6. Главный цикл отправляет .pwp через transport.sendFrame()
7. При process OK:
   - Если это proof → сразу approved (см. 4.3)
   - Если обычный файл → ждём пруф от получателя
8. При получении пруфа → чанк из waiting/ в approved/
9. Когда все чанки в approved/ → удалить каталог передачи
```

### 4.2. Приём

```
1. Получаем PW-кадр типа 'F'
2. assembleFile() сохраняет чанк в inbox/<peerIp>/<uuid>/waiting/
3. Если это первый чанк (waiting=1, parent=0):
   - Отправляем single-пруф [part]
   - Переносим чанок из waiting/ в parent/
4. Если все чанки получены:
   - Отправляем batch-пруф [все части]
   - Переносим все чанки из waiting/ в parent/
   - Склеиваем финальный файл в inbox/<peerIp>/
   - Удаляем каталог uuid/
5. proofAvailableChunks() периодически проверяет таймауты:
   - Если прошло >5 минут с последнего чанка → отправляем повторный пруф
```

### 4.3. Обработка пруфов

```
При получении файла с именем "PF":
1. processIncomingProof(uuid, parts)
2. Находит каталог spool/<peerIp>/<uuid>/
3. Для каждой части в parts:
   - Переносит чанк из waiting/ в approved/
   - Удаляет соответствующий .pwp
4. Если все чанки в approved/:
   - Обычный файл → переносит из work/ в sent/
   - Proof-файл → просто удаляет из work/
   - Удаляет каталог передачи
```

## 5. Жизненный цикл файла

### Отправка (обычный файл)

```
outbox/<ip>/file.pdf
    ↓ scanOutboxAll + spoolFile
spool/<ip>/<uuid>/0-5-0-file.pdf ... 4-5-0-file.pdf
outbox/<ip>/work/file.pdf
    ↓ prepareWaitingPackets
spool/<ip>/<uuid>/waiting/0-5-0-file.pdf
spool/0-5-0-<ip>-<uuid>.pwp
    ↓ transport.sendFrame
    ↓ process OK
    ↓ ждём пруф от получателя
    ↓ получили пруф
spool/<ip>/<uuid>/approved/0-5-0-file.pdf
    ↓ все чанки в approved
outbox/<ip>/sent/file.pdf
spool/<ip>/<uuid>/ удалён
```

### Приём

```
PW-кадр 'F'
    ↓ assembleFile
inbox/<ip>/<uuid>/waiting/0-5-file.pdf
    ↓ первый чанк → отправляем пруф
inbox/<ip>/<uuid>/0-5-file.pdf
    ↓ все чанки → отправляем batch-пруф
inbox/<ip>/<uuid>/*.pdf → склейка
inbox/<ip>/file.pdf
inbox/<ip>/<uuid>/ удалён
```

## 6. Ключевые компоненты

### 6.1. `File` (file.h/cpp)

Управление файлами и спулом:
- `scanOutboxAll()` — поиск файлов для отправки
- `spoolFile()` — нарезка на чанки
- `prepareWaitingPackets()` — упаковка чанков в .pwp
- `getPwpFiles()` — список готовых пакетов
- `assembleFile()` — приём и сборка чанков
- `proofAvailableChunks()` — проверка таймаутов

### 6.2. `Proof` (proof.h/cpp)

Логика пруфов:
- `sendFileProof(ip, uuid, parts)` — создание файла пруфа
- `processIncomingProof(uuid, parts)` — обработка входящего пруфа

### 6.3. `Words` (words.h/cpp)

Сериализация PW-кадров:
- `buildFileFrame()` — сборка кадра 'F'
- `parseFile()` — разбор кадра 'F'
- `buildEnv()` / `parseEnv()` — конверт (маршрутизация, пока не используется)

### 6.4. `main.cpp`

Главный цикл:
- Опрос `transport.poll(100)` каждые 100мс
- Обработка входящих кадров через `EBParser::parseEmsg()`
- Отправка `.pwp` с задержкой `sendTXDelay + random`
- Отслеживание процессов через `RunningProcess`

## 7. Конфигурация (config)

```cpp
config.workDir          // рабочая директория

```
